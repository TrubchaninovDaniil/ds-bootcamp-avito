## Какие данные и признаки использовал и почему?

### Для построения системы поиска использовались две группы признаков: 

### Текстовые данные (для оценки лексической релевантности):

*item_title_raw*, *item_infm_params_text*, *item_description_raw*.

Был применён метод Zone Weighting: заголовок дублируется 3 раза, параметры 2 раза и описание 1 раз. Это гарантирует, что точное совпадение слов в заголовке дает больший скор, чем случайное упоминание в длинном описании. Для запроса также применялось дублирование относительно параметров фильтрации.

### Метаданные (для хард-фильтрации и ранжирования):

*item_location_id / search_location_id*

*item_category_id / search_category*

В локальном классифайде (Авито) геолокация и рубрика критически важны. Идеальное текстовое совпадение из другого города бесполезно для пользователя, ищущего услугу здесь и сейчас.

## Какие модели или алгоритмы применил?

### Решение разбито на два этапа (First-stage retrieval + Geocategory Re-ranking):

Алгоритмом поиска является BM25Okapi (rank_bm25).
Оценка релевантности документа $D$ поисковому запросу $Q$ вычисляется по формуле:

$$\text{score}(D,Q) = \sum_{q_i \in Q} \text{IDF}(q_i) \cdot \frac{\text{TF}(q_i, D) \cdot (k_1 + 1)}{\text{TF}(q_i, D) + k_1 \cdot \left(1 - b + b \cdot \frac{\vert{}D\vert{}}{\text{avgdl}}\right)}$$

Где $\text{TF}(q_i, D)$ — частота токена, $\text{IDF}(q_i)$ — обратная частота документа в корпусе, $\vert{}D\vert{}$ — длина текущего документа, а $\text{avgdl}$ — средняя длина документов в базе.

Гиперпараметры: $k_1 = 1.2$, $b = 0.4$.

Значение $b$ намеренно занижено ($0.4$ вместо стандартных $0.75$), чтобы смягчить штраф за длину документа.

Используется препроцессинг. Регулярные выражения для очистки пунктуации + *SnowballStemmer*  для объединения словоформ. Для ускорения повторных запусков реализована потоковая токенизация датасета с сериализацией в *jsonl.gz*.

Особую роль играет алгоритм ранжирования: отбор TOP_K = 1500 кандидатов по bm25, после чего применяется лексикографическая сортировка (numpy.lexsort). По приоритетам с право на лево cовпадение локации, 
cовпадение категории, cкор BM25.

### Как проверял качество решения до отправки?

Написан автоматический скрипт sanity_check.py, который валидирует формат сабмита (отсутствие дубликатов, строго 50 item_id, отсутствие пустых значений) и замеряет Geo Match Rate и Category Match Rate для топ-1 выдачи, подтверждая корректность работы numpy.lexsort.

Проводил проверки потребления RAM и скорости инференса. Для оптимизации внедрен переход с Pandas Series на сырые C-массивы NumPy (.values) на этапе сортировки 1500 кандидатов, что ускорило цикл обработки запросов.

### Какие типы ошибок нашёл при анализе и что с ними сделал?

Была проблема пропусков локальных кандидатов в узких категориях. Ошибка была реша увеличением пула первичного ретривала *TOP_K_CANDIDATES* с 500 до 1500. Это позволило алгоритму дотягиваться до местных объявлений даже при слабом текстовом совпадении.

Следующая проблема это переполнение оперативной памяти при индексации корпуса. Пайплайн переведен на потоковую обработку с кэшированием. Вместо хранения всех данных в памяти, токенизированный корпус сжимается и построчно пишется на диск в item_corpus.jsonl.gz. При загрузке в BM25 используется потоковое чтение. Дополнительно внедрено чтение только нужных колонок Parquet-файла, явное удаление тяжелых объектов и принудительный вызов Garbage Collector.
